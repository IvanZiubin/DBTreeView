# Stage 2 (base-structure) — Backend plan

Machine-executable companion: [stage-2-backend.yaml](stage-2-backend.yaml).

## Goal

A runnable backend skeleton:

- PostgreSQL 16 holds one `nodes` table with a seeded tree (30 nodes, 3 roots, 5 levels).
- A .NET 8 minimal API (`backend/src/TreeEditor.Api`) serves the stage-2 endpoints from `docs/ai/api-contract.yaml`: `GET /api/health`, `GET /api/nodes/roots`, `GET /api/nodes/{id}/children`, `GET /api/nodes/{id}` (with `ancestorIds`), `POST /api/reset`, and a `POST /api/nodes/apply` stub that returns 501.
- On startup the API applies EF Core migrations and seeds the table if it is empty. It retries while the database is still starting.
- `docker-compose.yml` at the repo root runs `db`, `api` and `ui`.
- The test project (`backend/tests/TreeEditor.Api.Tests`) uses a `WebApplicationFactory<Program>` fixture backed by a Testcontainers PostgreSQL 16 container. It includes one health smoke test and a full test plan that docs-and-tests will implement.

## Decision record 1 — Tree storage model

**Context.** The tree has arbitrary depth, is too large to load in full, and parent links never change. Stages 2–4 need these operations:

1. Lazy children: direct children of one node, plus a `hasChildren` flag per node.
2. Ancestor lookup when a node is loaded into the cache (`ancestorIds`, ordered root to parent).
3. Subtree soft delete that includes descendants never loaded by any client.
4. Inserts under nodes created in the same Apply batch (a temp parent gets its real id inside the transaction).
5. Transactional Apply (stage 3), plus a Reset that restores fixed ids.

**Options**

| Option | Lazy children | Ancestors | Subtree delete | Insert (incl. under new node) | Reset / seed | Cost |
|---|---|---|---|---|---|---|
| **Adjacency list (`parent_id`) + recursive CTE** | One indexed lookup on `parent_id` | Recursive CTE that walks up through PK lookups; O(depth) | One recursive CTE `UPDATE` | One row with only the parent's id. Trivial once the parent's id is known | Plain multi-row insert | Recursion cost on deep subtrees. PostgreSQL handles this well with a `parent_id` index |
| Materialized path (`path` text/ltree) | Needs `parent_id` or a path-depth filter; `ltree` gives `path ~ 'a.b.*{1}'` | Parse the path; no query needed | `WHERE path <@ 'a.b'`, one indexed statement | The child path needs the parent's path *and* its own id. With identity ids that means insert then update (or `nextval` first). Path length grows with depth | Paths must be seeded and kept consistent | Redundant data, the extra `ltree` extension, and two-step inserts |
| Closure table (`ancestor, descendant, depth`) | `depth = 1` join | One indexed select | One join `UPDATE` | Copy every ancestor row of the parent, plus a self row. O(depth) rows per insert | Seed must generate O(n·depth) rows | Second table, write amplification, and two tables to keep consistent across Reset and Apply |
| Nested sets | Awkward | Range query | Range update | Renumbers half the tree on every insert | Recompute everything | Not a fit for frequent inserts |

Immutable parents remove the main weakness of path and closure models (moves), but they do not make inserts cheaper. The workload is dominated by single-level reads, short upward walks and occasional subtree deletes. All of these are a single SQL statement with an adjacency list and a recursive CTE.

**Decision.** Use an adjacency list: `nodes(id bigint identity PK, parent_id bigint NULL FK -> nodes(id), value varchar(200), is_deleted boolean)`. Ancestors and subtrees use `WITH RECURSIVE` raw SQL. Ordinary reads use EF Core LINQ.

**Supporting constraints and indexes**

- `pk_nodes` on `id`. Each upward CTE step is a PK lookup.
- `ix_nodes_parent_id_id` on `(parent_id, id)`. It serves children ordered by id, roots (`parent_id IS NULL ORDER BY id`), the `EXISTS` check behind `hasChildren`, and the downward CTE join. EF uses it to cover the FK, so there is no separate FK index.
- `fk_nodes_parent` with `ON DELETE RESTRICT`. Rows are never physically deleted outside `TRUNCATE` in Reset.
- `ck_nodes_parent_not_self`: `parent_id IS NULL OR parent_id <> id`.
- `ck_nodes_value_length`: `char_length(value) BETWEEN 1 AND 200` (matches the contract's value rule).
- Trigger `trg_nodes_parent_immutable` (`BEFORE UPDATE OF parent_id`) raises SQLSTATE 23514 if `parent_id` changes. This enforces "existing parent–child relationships cannot be changed" in the database itself. Because a parent must already exist when a child is inserted, and links never change, cycles are impossible.

**Consequences**

- `GET children` and `GET roots` are a single indexed LINQ query with `EXISTS` for `hasChildren`.
- `GET /api/nodes/{id}` runs a node query plus the ancestor CTE. Both are stable without a transaction because links are immutable.
- Stage 3 cascade delete is one statement (see "Stage 3 readiness").
- Invariant from stage 3 on: **a deleted node's descendants are all deleted**. Cascade enforces it, and adds under a deleted parent are rejected with 409. Because of this, a node loaded after an ancestor was deleted already comes back with `isDeleted=true` (roadmap stage 4 edge case) without any read-time ancestor check.

**One-liner for CLAUDE.md Decisions:**
`Tree storage: adjacency list (nodes.parent_id, immutable via trigger) + recursive CTEs for ancestors/subtree soft-delete; index (parent_id, id) — see docs/plans/stage-2-backend.md#decision-record-1--tree-storage-model`

## Decision record 2 — Migrations

**Options:** hand-written migration plus snapshot, or a migration generated by `dotnet ef`.

**Decision:** generated. The implementer runs `dotnet ef migrations add InitialCreate` (local tool manifest, dotnet-ef 8.0.11), then makes one hand edit: add the trigger SQL with `migrationBuilder.Sql` to `Up`, and drop it in `Down`.

**Why:** a generated snapshot is guaranteed consistent, and `dotnet ef migrations has-pending-model-changes` (EF 8) becomes an acceptance check. A hand-written snapshot is a common source of silent drift. The timestamped file name is the only non-deterministic part; steps refer to it by the glob `Data/Migrations/*_InitialCreate.cs`.

## Decision record 3 — Seed shape: multiple roots

There are 3 roots, 30 nodes and 5 levels, with fixed ids 1..30 in breadth-first order. Every parent id is lower than its child's id.

Why multiple roots:

- The contract already returns `Node[]` for roots.
- Multiple roots exercise CachedTreeView's handling of sibling roots, and of "gaps" across independent trees. For example, load 26 and 30: they belong to different roots and have no shared ancestor.
- Deleting one whole root still leaves the others usable for testing.

Each root has a 5-level branch, so the "≥4 levels" requirement holds on all three. Leaves sit at levels 3, 4 and 5, so `hasChildren=false` shows up at several depths.

## Decision record 4 — Seeding and Reset

There is one `TreeSeeder` class (scoped service):

- `SeedIfEmptyAsync` runs at startup. If the table is empty, it inserts the seed in one transaction.
- `ResetAsync` runs in one transaction: `TRUNCATE TABLE nodes RESTART IDENTITY`, then the seed insert.
- Both use the same private `InsertSeedAsync`. It is a single `INSERT … SELECT FROM unnest(@nodeIds, @parentIds, @nodeValues)`, so FK order inside the batch does not matter. Then `setval(pg_get_serial_sequence('nodes','id'), MAX(id))`, so the next generated id is 31. Root parents are passed as `0` and turned back into `NULL` with `NULLIF`, which avoids nullable-array parameter binding.

`TRUNCATE` is transactional in PostgreSQL. It takes an ACCESS EXCLUSIVE lock, so concurrent resets and reads serialize behind it.

## Decision record 5 — Startup and retry

`DatabaseInitializer.InitializeAsync` runs after `app.Build()` and before the endpoints are mapped. It tries up to 30 times, 2 s apart (about 60 s). Each attempt runs `MigrateAsync` and then `SeedIfEmptyAsync` in a fresh DI scope; on any exception it logs a warning and retries. Compose also waits for `db` to report `service_healthy`, so the retry is a second line of defence (for example during the first-run initdb restart). Npgsql `EnableRetryOnFailure` is deliberately **not** enabled: it conflicts with the user-initiated transactions used by Reset and Apply.

`dotnet ef` design-time tooling stops the host at `Build()`, so the initializer never runs during `migrations add`.

| POST | `/api/reset` | `Features/Reset/ResetEndpoints.cs` (group `/api`) | 200 roots after reset |
| POST | `/api/nodes/apply` | `Features/Apply/ApplyEndpoints.cs` (group `/api/nodes`) | 501 ProblemDetails, title "Not Implemented". The body is not bound in stage 2 |

`hasChildren` = `EXISTS` child row; deleted children count. Ancestor SQL (raw, via `Database.SqlQuery<long>`):

```sql
WITH RECURSIVE ancestors AS (
    SELECT p.id, p.parent_id, 1 AS depth
    FROM nodes c
    JOIN nodes p ON p.id = c.parent_id
    WHERE c.id = @id
    UNION ALL
    SELECT p.id, p.parent_id, a.depth + 1
    FROM ancestors a
    JOIN nodes p ON p.id = a.parent_id
)
SELECT a.id AS "Value" FROM ancestors a ORDER BY a.depth DESC
```

## Test design

- `ApiFactory : WebApplicationFactory<Program>, IAsyncLifetime` owns a `PostgreSqlContainer` (`postgres:16`). It sets environment `Testing` and `ConnectionStrings:Default` through `UseSetting`. Startup migrations and the seed run against the container.
- `[CollectionDefinition("api")] ApiCollection : ICollectionFixture<ApiFactory>` gives one container for the whole run, and tests run sequentially.
- `IntegrationTestBase : IAsyncLifetime` calls `Factory.ResetDatabaseAsync()` (`TreeSeeder.ResetAsync`) before **every** test, which isolates tests with no ordering dependencies. Each test class carries `[Collection(ApiCollection.Name)]` itself.
- Tests mutate state directly through `Factory.WithDbAsync(db => …)`, then go through HTTP.
- Test cases are listed under `test_plan` in the yaml. They cover health, roots, children (incl. leaf, `hasChildren` with a deleted child, 404), node details (ancestors at depths 1/2/3/5, 404, non-numeric id), reset (values, flags, count, sequence restart), the apply stub (501 problem+json), an unknown route (404 problem+json), and DB constraints (parent immutability trigger, self-parent check).

## Stage 3 readiness (why the model is sufficient)

- **Transaction:** `await using var tx = await db.Database.BeginTransactionAsync(IsolationLevel.ReadCommitted)`. The first statement is `SELECT pg_advisory_xact_lock(4242)`, which serializes concurrent Applies. This closes the race where one Apply adds a child under P while another cascades from P's ancestor: the cascade CTE's snapshot would not see the uncommitted child.
- **Adds:** topologically sort by `parentTempId` (cycle → 400). Insert in dependency order with EF `SaveChangesAsync` per add, or with `INSERT … RETURNING id`, and fill `idMap`. Check that each real parent exists (404) and is not deleted (409).
- **Edits:** `UPDATE nodes SET value = @v WHERE id = @id` after the 404/409 checks.
- **Cascade delete:** one statement:

```sql
WITH RECURSIVE subtree AS (
    SELECT n.id FROM nodes n WHERE n.id = ANY(@ids)
    UNION
    SELECT c.id FROM nodes c JOIN subtree s ON c.parent_id = s.id
)
UPDATE nodes SET is_deleted = TRUE
WHERE id IN (SELECT id FROM subtree) AND is_deleted = FALSE;
```

- **Response nodes:** reuse `NodeQueries.GetNodeDetailsAsync` per id, or batch the ancestor CTE with an `origin` column.

Nothing in stage 3 needs a schema change.

## Risks

- **Host port 5432 or 8080 already in use** (for example a local Postgres) makes `docker compose up` fail. This is documented in the smoke notes; there is no workaround in this plan.
- **Testcontainers on macOS** needs a reachable Docker socket. Docker Desktop provides one. With other runtimes (Colima), `DOCKER_HOST` must be set.
- **`docker compose up --build`** for the full stack needs `frontend/Dockerfile` from the frontend plan. Backend acceptance therefore uses `docker compose up --build -d db api`.
- **Development environment** shows the developer exception page (stack traces) for local `dotnet run`. Compose runs `Production`, and tests run `Testing`, so the contract's "no stack trace" holds where it is checked.
- **Generated migration file name** contains a timestamp. Steps reference it by glob.
